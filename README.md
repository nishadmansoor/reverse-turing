# Reverse Turing Test

An ensemble of three independent classifiers that judge whether text was written
by a human or generated by a language model — a fine-tuned transformer, a
stylometric logistic regression, and a CNN that reads text as an image — combined
by a stacked meta-classifier.

## Results

Measured on the held-out **RAID** test split (n = 12,000). No model saw these
rows during training, and the meta-classifier was fitted on the validation
split rather than on training data. These are the int8 models the deployed
app actually serves.

| Model | Accuracy | F1 | ROC AUC | vs. baseline |
|-------|---------:|---:|--------:|-------------:|
| Transformer (DistilBERT) | 98.79% | 98.83% | 99.94% | +47.3 pts |
| Visual CNN | 97.54% | 97.61% | 99.64% | +46.0 pts |
| Stylometric | 76.78% | 78.67% | 76.89% | +25.3 pts |
| **Ensemble (stacked)** | **99.25%** | **99.27%** | **99.95%** | **+47.7 pts** |

Majority-class baseline: 51.51%. The ensemble outperforms every individual
model, and precision and recall stay balanced across both classes
(Human 0.9928 / 0.9911, AI 0.9916 / 0.9932).

Reproduce with `python src/train_meta.py --dataset raid --backend onnx`; the
full report is written to `results/evaluation_raid_int8.json`.

Quantization is free here: on the same split the int8 models match the fp32
originals to within noise (ensemble 99.25% vs 99.22%, identical 99.95% ROC AUC)
while being 4x smaller. Drop `--backend onnx` for the fp32 baseline.

## How it works

Three models read the same text and vote independently:

1. **Transformer** — DistilBERT fine-tuned for sequence classification, reading
   up to 256 tokens. Catches phrasing and semantics.
2. **Stylometric** — logistic regression over five features: average sentence
   length, sentence-length variance, average word length, vocabulary richness,
   and punctuation density. Cheap and fully interpretable.
3. **Visual CNN** — renders each text as a 224×224 heatmap (one row per
   sentence, one column per measurement) and classifies the resulting texture.
   It sees structural rhythm rather than words.

A **stacked meta-classifier** then combines their output probabilities. The
protocol matters:

```
base models      -> trained on the train split
meta-classifier  -> fitted on the val split (data the bases never saw)
all reported numbers -> measured on the test split
```

Fitting the stacker on training data would let it learn from the base models'
overconfidence on rows they had memorised, inflating the ensemble's apparent
accuracy.

## Setup

```bash
git clone https://github.com/nishadmansoor/reverse-turing.git
cd reverse-turing
git lfs install && git lfs pull      # model weights are tracked via LFS

pip install -r requirements.txt      # runtime only
python app/app.py                    # http://localhost:5001
```

The app loads prebuilt artifacts from `artifacts/` and never reads the raw
dataset, so this works without downloading any data. It boots in a couple of
seconds.

To retrain or rebuild, install the training dependencies too:

```bash
pip install -r requirements-dev.txt
```

## Retraining

```bash
# 1. Prepare data (RAID is a ~12 GB download)
python src/raid_pipeline.py --download

# 2. Train base models  (transformer ~5 h on Apple MPS; CNN ~35 min)
python src/retrain.py --dataset raid
python src/retrain.py --dataset raid --only cnn stylo   # skip the slow one

# 3. Export + quantize to int8 ONNX for serving
python src/quantize.py

# 4. Fit the ensemble and evaluate on the test split
python src/train_meta.py --dataset raid --backend onnx

# 5. Rebuild the artifacts the app serves
python src/build_artifacts.py --dataset raid
```

`--dataset` is a required argument by design. Inferring it from whichever files
happen to exist on disk makes it possible to run a long training job against the
wrong corpus without noticing.

## Deployment

Both models are exported to int8 ONNX and served through onnxruntime, so the
container needs no torch at all:

| | fp32 + torch | int8 + onnxruntime |
|---|---|---|
| Model payload | 293 MB | **71 MB** |
| Resident memory | ~1.1 GB | **336 MB** |
| Ensemble accuracy | 99.22% | 99.25% |

That fits a 512 MB free tier.

**Render** — `render.yaml` is a Blueprint. On render.com choose
New > Blueprint and connect this repository. Free instances sleep after
15 minutes idle, so the first request after a pause takes about a minute.

**Anywhere else** — it is a plain container that reads `$PORT`:

```bash
docker build -t reverse-turing .
docker run -p 7860:7860 reverse-turing
```

Hugging Face Spaces now requires a PRO subscription for Docker and Gradio
Spaces; only static Spaces are free. `deploy/deploy_hf.sh` still works with PRO.

## Datasets

| | Samples | Notes |
|---|---|---|
| **RAID** (current) | 156k prepared splits | Many modern generators, 8 domains, adversarial attacks |
| HC3 | 168k | Early-ChatGPT era; kept for comparison |

RAID is materially harder: the stylometric model scores ~91% on HC3 but only
~77% on RAID, because modern generators imitate human style far more closely.

## Project structure

```
reverse-turing/
├── app/
│   ├── app.py                 # Flask app — loads artifacts, no training
│   ├── examples.json          # Demo texts
│   └── templates/             # base, index, results, explore, about, error
├── src/
│   ├── features.py            # Shared feature extraction (single source of truth)
│   ├── model_defs.py          # Shared CNN architecture
│   ├── retrain.py             # Train base models
│   ├── quantize.py            # Export + quantize to int8 ONNX
│   ├── train_meta.py          # Fit + evaluate the stacking ensemble
│   ├── build_artifacts.py     # Precompute what the app serves
│   ├── pipeline.py            # HC3 data pipeline
│   └── raid_pipeline.py       # RAID data pipeline
├── artifacts/                 # Committed: PCA, explorer payload, metadata
├── models/
│   ├── onnx/                  # int8 graphs the app serves (71 MB)
│   └── ...                    # fp32 training outputs, via LFS
├── deploy/                    # Hugging Face Space config (needs PRO)
├── render.yaml                # Render Blueprint
└── Dockerfile
```

Feature extraction and the CNN architecture live in one module each and are
imported by both training and serving. They were previously copy-pasted across
four files, which is how the training and serving paths drift apart.

## Limitations

- **Short text is unreliable.** Below ~50 words the stylometric features are
  mostly noise.
- **Domain shift hurts.** These numbers are in-distribution for RAID. Text from
  a different domain, or a generator newer than the training data, will score
  worse.
- **Editing defeats it.** Human-revised generated text carries both signatures.
- **Not proof of authorship.** Every output is a probability.
