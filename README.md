# Reverse Turing Test

Can a model tell whether a model wrote this?

Three classifiers each read the same passage in a completely different way, and
a fourth model learns how much to trust each one. Together they decide whether
text was written by a person or generated by a language model.

**Live demo:** https://nishadmansoor.github.io/reverse-turing/

_Runs entirely in your browser — no server, nothing to wake up. The models
download once (~71 MB) on first use, then are cached._

## Results

Every number below is measured on 12,000 passages the models never saw during
training.

| Model | Accuracy | F1 | ROC AUC | vs. baseline |
|-------|---------:|---:|--------:|-------------:|
| Transformer (DistilBERT) | 98.79% | 98.83% | 99.94% | +47.3 pts |
| Visual CNN | 97.52% | 97.59% | 99.64% | +46.0 pts |
| Stylometric | 76.78% | 78.67% | 76.89% | +25.3 pts |
| **Ensemble (all three combined)** | **99.28%** | **99.30%** | **99.95%** | **+47.8 pts** |

The "vs. baseline" column compares against always guessing whichever class is
more common, which scores 51.51% here. That comparison matters: a model can post
a respectable-looking accuracy and still have learned nothing, and this is how
you catch it.

Combining the three beats any of them alone. Errors are also evenly split rather
than piling onto one class — precision and recall are 0.9938 / 0.9912 on human
text and 0.9918 / 0.9942 on generated text.

Reproduce with `python src/train_meta.py --dataset raid --backend onnx`. The full
report lands in `results/evaluation_raid_int8.json`.

## How it works

Each model looks for something different, so they fail in different ways — which
is the point of combining them.

1. **Transformer** — a fine-tuned DistilBERT that reads the passage as language,
   picking up on phrasing and meaning.
2. **Stylometric** — a logistic regression over five measurements: average
   sentence length, how much sentence length varies, average word length,
   vocabulary richness, and punctuation density. Cheap, and you can read exactly
   why it decided what it did.
3. **Visual CNN** — turns the text into a 224×224 heatmap image, one row per
   sentence and one column per measurement, then classifies the *texture*. It
   sees the rhythm of the writing rather than the words.

A fourth model (the **stacked meta-classifier**) takes those three probabilities
and produces the final answer. It is trained on a separate slice of data:

```
the three base models  ->  trained on the training split
the combining model    ->  trained on the validation split
every number reported  ->  measured on the test split
```

The separation is deliberate. The three base models are unusually confident about
examples they were trained on, so a combining model fitted on that same data
would learn to trust them more than it should, and the final accuracy would look
better than it really is.

## Setup

```bash
git clone https://github.com/nishadmansoor/reverse-turing.git
cd reverse-turing
git lfs install && git lfs pull      # model weights are stored with Git LFS

pip install -r requirements.txt      # just what's needed to run it
python app/app.py                    # http://localhost:5001
```

No dataset download required. The app reads small prebuilt files from
`artifacts/` instead of the raw corpus, and starts in about three seconds.

To retrain anything, install the heavier training dependencies as well:

```bash
pip install -r requirements-dev.txt
```

## Retraining

```bash
# 1. Download and prepare the data (RAID is a ~12 GB download)
python src/raid_pipeline.py --download

# 2. Train the three base models
#    (transformer ~5 h on Apple MPS; CNN ~35 min; stylometric seconds)
python src/retrain.py --dataset raid
python src/retrain.py --dataset raid --only cnn stylo   # skip the slow one

# 3. Convert the two neural models to int8 ONNX for serving
python src/quantize.py

# 4. Train the combining model and score everything on the test split
python src/train_meta.py --dataset raid --backend onnx

# 5. Rebuild the small files the app reads at startup
python src/build_artifacts.py --dataset raid
```

`--dataset` is required rather than guessed. If the script picked a dataset based
on whichever files happened to be sitting on disk, it would be easy to spend
hours training against the wrong corpus without noticing.

## Deployment

The site is static and runs the whole ensemble client-side, so there is no
inference server and no cold start. Both neural models are converted from
32-bit floats to 8-bit integers (quantization) and executed by ONNX Runtime Web
through WebAssembly; the stylometric and stacking models are a few lines of
arithmetic ported to JavaScript.

| | fp32 + PyTorch | int8 + ONNX Runtime Web |
|---|---|---|
| Model files | 293 MB | **71 MB** |
| Where it runs | a server you pay for | the visitor's browser |
| Per classification | 1.4-2.0 s (0.1 CPU instance) | **~0.4 s** |

Accuracy is unaffected — the int8 models match the fp32 originals to within
rounding noise, with identical 99.95% ROC AUC.

`docs/` is the published site. GitHub Pages serves a repository's `/docs`
folder, which is why it carries that name. The model files there are ordinary
git objects, **not** Git LFS, because Pages serves LFS pointer files as text
instead of resolving them.

Rebuild it after retraining:

```bash
python src/quantize.py        # int8 ONNX graphs
python src/export_web.py      # model parameters + parity fixture
cp models/onnx/*.onnx docs/models/
```

A container build is also kept for running it as a server:

```bash
docker build -t reverse-turing .
docker run -p 7860:7860 reverse-turing
```

### Checking the port

The JavaScript reimplementation has to match the Python pipeline exactly. A
silent mismatch would feed the models different inputs than they were trained
on and quietly degrade predictions without ever raising an error, so
`src/export_web.py` writes a fixture of Python-generated values and
`docs/parity.html` replays it in the browser, failing loudly on any
divergence. All 27 cases pass, including float32 rounding in the heatmap
encoding and OpenCV's exact colour-map table.

## Datasets

| | Samples | Notes |
|---|---|---|
| **RAID** (current) | 156k prepared splits | Many modern generators (GPT, Llama, Mistral, MPT) |
| HC3 | 168k | Early-ChatGPT era; pipeline kept for comparison |

All reported figures are on RAID. HC3 only covers a single 2022-era generator,
which makes it both easier and less representative, and the difference is
measurable: the same stylometric model scores ~91% on HC3 but only ~77% on RAID.
Today's generators imitate human writing far more closely.

```

├── app/

│   ├── examples.json          # Labelled demo passages

├── src/

│   ├── model_defs.py          # CNN architecture (one definition, shared)
│   ├── retrain.py             # Train the base models
│   ├── quantize.py            # Convert to int8 ONNX
│   ├── export_web.py          # Export params + parity fixture for the browser
│   ├── train_meta.py          # Train the combining model + score on test
│   ├── build_artifacts.py     # Precompute what the app reads at startup
│   ├── pipeline.py            # HC3 data prep
│   └── raid_pipeline.py       # RAID data prep
├── docs/                      # The published static site (GitHub Pages)
│   ├── index.html             # Classifier — runs the models in-browser
│   ├── js/features.js         # JS port of src/features.py (parity-checked)
│   ├── js/engine.js           # ONNX Runtime Web inference
│   ├── models/                # int8 graphs, plain git (not LFS)
│   └── parity.html            # Replays Python values against the port
├── artifacts/                 # PCA, explorer data, build metadata
├── models/
│   ├── onnx/                  # int8 models the app serves (71 MB)
│   └── ...                    # full-precision training outputs, via Git LFS
├── render.yaml                # Optional container deployment
└── Dockerfile
```

Feature extraction and the CNN architecture each live in exactly one file, used
by both training and serving. They used to be copy-pasted across four files,
which is how the code that trains a model and the code that runs it quietly
drift apart and stop agreeing.

## Limitations

- **Short text is unreliable.** Under roughly 50 words, the stylometric
  measurements are mostly noise.
- **It works best on text like its training data.** RAID's raw file is ordered by
  topic and the loader reads it start to finish, so these splits come mostly from
  one of RAID's eight domains. Text from a different domain — or from a generator
  newer than the training data — will score worse.
- **Editing defeats it.** Generated text that a person has revised carries both
  signatures at once.
- **This is not proof of authorship.** Every answer is a probability, not a
  verdict. Don't use it to accuse anyone of anything.
